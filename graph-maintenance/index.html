Memory graph maintenance

Memory that cleans up after itself.

Most agent memory systems focus on retrieval: find an old note and stuff it back into context. OpenClawBrain goes further. It maintains what the agent remembers, so memory can get cleaner, safer, and more useful over time.

The problem

Old memory is not automatically good memory. A memory can be relevant and still be wrong, stale, too broad, superseded, private, or dangerous to use in the current turn.

That is why OpenClawBrain separates two jobs:

Memory Authority

Decides whether a retrieved memory can influence this turn. Relevance is not authority.

Graph Maintenance

Decides how the graph should evolve after many turns, corrections, outcomes, and stale facts.

What it maintains

Fewer duplicate memories

Exact duplicates can be consolidated into a canonical memory while preserving lineage and proof.

Safer edges

Edges to missing, deleted, or tombstoned nodes can be retired instead of silently polluting retrieval.

Stale authority checks

Old high-impact memories can be flagged for review before they keep steering future work.

Scoped exceptions

A broad default like "be concise" should not erase a local instruction like "go deep for this critique."

Privacy-safe forgetting

Tombstones block recapture without putting the forgotten content back into proposals or proof.

Local proof

Every applied mutation leaves a redacted proof event, lineage row, or edge observation.

The safety line

Graph maintenance is not allowed to become a hidden second authority system. It can provide features and proposals. Memory Authority still recomputes the turn-level decision every time.

retrieve candidates
  -> Memory Authority decides turn-level use
  -> agent acts
  -> outcomes and corrections become evidence
  -> Graph Maintenance proposes safe graph changes
  -> proof and lineage record what changed

Connectivity is not authority. A behavioral edge is not proof that a fact is true. Repeated retrieval is not repeated confirmation.

Operator commands

You can ask your OpenClaw agent from Telegram or any OpenClaw command surface:

/brain graph health
/brain graph dry-run
/brain graph proposals
/brain graph explain <proposalId>
/brain graph apply <proposalId>
/brain graph reject <proposalId>
/brain graph stale
/brain graph clusters
/brain graph tombstones

Low-risk deterministic proposals can be applied. Semantic merges, privacy changes, stale high-authority changes, scoped exceptions, and tombstone recapture checks stay review-gated.

Codex from Telegram

The same philosophy powers the Codex continuity workflow. Codex UI stays the high-bandwidth workbench at the computer. OpenClaw/Telegram becomes the mobile operator surface. OpenClawBrain decides what is worth surfacing.

/brain codex status
/brain codex threads
/brain codex watch --latest
/brain codex handoff

Telegram should not become a noisy coding UI. It should send concise completion, failure, blocker, approval-needed, and auth-failure updates when you explicitly watch a Codex task.

The product difference

Generic memory stores retrieve. OpenClawBrain governs and maintains.

That means provenance, scope, validity, correction, forgetting, and proof are part of the product, not afterthoughts. The goal is not more memory. The goal is fewer, better memories that the agent can use with judgment.
